# Round 9: multiple machines (P1)

The user wants Relay to drive agents on more than one machine. The first remote is a cloud VM (Linux) that runs herdr and the agents. The app pairs with each machine's bridge separately.

Read first: `../../../AGENTS.md`, `../../api.md` (Transport, Pairing, Machine), `../round-8/README.md`.

## Decisions (made with the user)
- **One bridge per machine.** Each machine runs `relay` next to its own herdr. The phone talks to each bridge directly over Tailscale, with that machine's own token. No proxy through the Mac.
- **Sidebar machine menu:** **All** (the default) plus one entry per machine, each with an online dot.
  - In All, project sections carry a machine tag.
  - "Now" and approvals span every machine.
  - Picking one machine shows only its agents.
- **Remote setup is manual in P1:** copy the binary, run `relay install-systemd`, then `relay pair`. The `relay remote add` automation is P2, not now.
- **Out of scope:**
  - pair-once discovery through the Mac;
  - `relay remote add` / `update`;
  - push and widgets.
- **No wire changes to existing routes.** Each bridge is unchanged apart from the dev-only env overrides below.
- The Go bridge lives in `bridge-go/`. The cutover to `bridge/` is pending the user, so don't touch `bridge/` (Swift).

## What each session builds
**mm-bridge. Do this first: the api.md section within about 30 minutes, then message everyone.**
- api.md "Multiple machines" section:
  - the app keeps a list of pairings keyed by `GET /machine` `id`;
  - re-pairing a machine it already knows replaces that entry (new URL or token);
  - each bridge is independent;
  - agent and workspace ids are only unique per machine, so the app keys by machine + id.
- `docs/remote-setup.md`: step by step for a Linux VM.
  - Install Tailscale.
  - Build the binary with `scripts/build-linux.sh` (amd64 + arm64, `CGO_ENABLED=0`, version stamped) and copy it over.
  - herdr socket path.
  - `relay install-systemd` + `systemctl --user enable --now`, and `loginctl enable-linger` so it runs without a login.
  - `relay pair`.
  - Firewall: the bridge binds the Tailscale IP only.
  - Updating, logs, and uninstalling.
- Dev/test overrides in the Go bridge:
  - env `RELAY_MACHINE_ID` / `RELAY_MACHINE_NAME` replace what `/machine` reports, so a second local bridge shows up as another machine. Document them as test-only.
  - `relay pair --url <base>` if the auto-detected URL is wrong (NAT, several tailnet IPs).
- `scripts/second-bridge.sh` starts a Go bridge for app testing:
  - port 7881;
  - temp `RELAY_HOME`;
  - `RELAY_MACHINE_ID=test-vm`, `RELAY_MACHINE_NAME="Test VM"`;
  - same herdr;
  - it prints a pair link for `127.0.0.1:7881`.
- Verify `install-systemd` for real in a systemd-enabled Linux container (podman, e.g. `fedora` or `ubuntu` with systemd as PID 1): the unit starts, restarts on crash, and serves `/health`.

**mm-data**
- **Pairings:** `PairingStore` becomes a list keyed by machine id.
  - The Keychain account is the machine id; the list goes in the App Group defaults.
  - Migrate the existing single pairing: call `/machine` to learn its id. If the bridge is offline, keep it under a provisional id and fix it up on the first successful `/machine`.
- **Store:** the store drives N machine connections. Each machine gets its own backend, WS, reconnect and backoff, and one machine being offline never blocks the others.
- **App-wide agent key = machine id + agent id.** It covers selection, seen, archive, drafts, pending sends, controls caches, live replies, remembered expansion, and deep links.
  - The simplest route is probably a namespaced string key, so the existing `[String: …]` maps keep working, with the raw pane id used only at the API boundary. Pick what's cleanest and explain it in your report.
  - Migrate the persisted keys (`selectedAgentId`, `seenAgents`, `archivedAgents`, `sessionFilter` etc.) to the migrated machine's id.
- **Per-machine status:** `connecting` / `online` / `offline` / `needsRePair`, plus name, kind, os and bridge version (from `/health`).
- **API for mm-ui:**
  - the machines list;
  - selected machine filter (`nil` = All);
  - agents across machines with their machine;
  - add (pair link), rename (local label), remove, re-pair;
  - usage per machine.

  Agree it by herdr message early. Write it in `docs/tasks/round-9/interfaces.md`.
- **Mock:** two machines ("Mock MacBook Pro" + "Mock VM", Linux, `desktop`), including:
  - an overlapping pane id on both;
  - one machine that can be made offline.
- **Unit tests:** keying, migration of pairings and defaults, and the per-machine connection state.

**mm-ui**
- **Machine menu** (`SidebarToolbar.swift`): All + each machine, with a dot (online / offline / re-pair needed), a checkmark on the current choice, and "Add machine…" and "Manage machines…" at the bottom. The toolbar capsule shows "All machines" or the machine name.
- **Sidebar:**
  - In All, project sections from different machines never merge. The header shows the project name plus a small secondary machine tag, and only when more than one machine is paired.
  - "Now" and approvals cover all machines, and rows show the machine in the subtitle when in All.
  - Offline machines' agents show a greyed "offline" state instead of vanishing.
- **Machines screen** (from the ••• menu and the machine menu):
  - list with status, OS and version;
  - rename (local only);
  - re-pair (scan or paste);
  - remove, with a confirm;
  - Add machine (the same QR/paste pairing flow as first launch, reused from `PairingView`).
- **New chat:** pick the machine when All is selected, defaulting to the last used.
- **Usage:** merge by subscription (same provider + plan) across machines. Where it isn't clearly the same account, show per machine.
- **Accessibility:** keep 44 pt targets, VoiceOver labels (e.g. "Machine: Test VM, offline"), and Dynamic Type.
